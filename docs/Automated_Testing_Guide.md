# Automated testing evidence guide

## Scope found in the prototype

BloodConnect is a Vite/React frontend with an Express/MySQL backend. Roles are donor, hospital, admin, and super-admin. The operational workflow is donor registration/login and donation scheduling, hospital inventory/donation/request handling, and admin inventory, transfer/request, donor, partner, announcement, MBD, ranking, and feature-flag management.

Analytics rules are implemented in `frontend/src/admin/analyticsEngine.js`: completed/partial requests provide historical demand; seven-day shortage demand is 30-day requested demand divided by 30 and multiplied by 7; expired stock is excluded; near-expiry stock is limited by demand before its expiry; trend thresholds are +/-10%; donor recovery is 90 days whole blood, 14 platelets, and 28 plasma. The backend wastage controller scores expiry (5--40), historical wastage (capped at 30), demand (5/10/20), and inventory (0/5/10); its allocator assigns compatible expiring inventory by request priority (critical, urgent, normal).

Relevant API groups are `/api/auth`, `/api/user`, `/api/hospital`, `/api/admin`, `/api/notifications`, and public feed/ranking/feature-flag endpoints. MySQL access is through `backend/db.js` and model/controller queries. No test connects to production records.

## Tools and isolation

* **Vitest** runs deterministic analytics unit tests and produces an HTML report.
* Node's built-in test runner exercises Express API routing and validation with the pool stubbed where needed.
* **Playwright** runs browser workflows. It intercepts every API request and uses only in-memory responses; it never sends test credentials or writes to MySQL.
* The existing guarded database simulation (`backend/scripts/createAnalyticsSimulationDb.js`) creates only databases ending in `_simulation`, disables schedulers with `SIMULATION_MODE=true`, and can be used for true MySQL integration checks. It refuses unsafe target names.

## Run

```powershell
cd frontend
npm.cmd install
npm.cmd run test:unit:report
npm.cmd run test:e2e

cd ..\backend
npm.cmd test
$env:DB_NAME='bloodconnect_simulation'
$env:SIMULATION_MODE='true'
npm.cmd run test:simulation-integration
```

For the isolated MySQL integration workflow (never point this at production):

```powershell
cd backend
npm.cmd run simulation:db:create
npm.cmd run simulation:db:test
$env:DB_NAME='bloodconnect_simulation'
$env:SIMULATION_MODE='true'
npm.cmd run dev
```

## Evidence and interpretation

Generated evidence is written locally and is intentionally ignored as run output: `frontend/.vitest/index.html`, `frontend/test-results/e2e-html/index.html`, `frontend/test-results/evidence/*.png`, Playwright failure traces/screenshots in `frontend/test-results/e2e-artifacts`, and `backend/simulation/output/validation-report.json`. The HTML reports record each test name/ID, duration, observed assertion/status, and failure details; the controlled simulation JSON additionally records expected and actual values per check. Test data is intercepted browser data or the guarded simulation database, and can be removed by deleting only the named simulation database when no longer needed.

A pass establishes reproducible conformance to the implemented rules and controlled inputs. It does not establish real-world forecast accuracy, clinical validity, or production-database behavior.
